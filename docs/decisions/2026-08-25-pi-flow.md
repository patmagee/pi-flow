# Pi-native design and delivery workflow

## Context

Superpowers provides strong brainstorming, planning, test-driven development, and review behavior. Its Pi integration still assumes that subagents are the default execution unit. In a measured implementation session, one plan task launched an implementer, reviewer, two fixers, and two re-reviewers. Repeated metadata inspection also returned tool results near Pi's 50 KB limit.

Pi Flow must preserve design quality while reducing agent turns, repeated context reconstruction, and duplicate review loops.

## Decision

Pi Flow is a separate Pi package with six skills and one small extension:

1. `designing-changes` preserves interactive exploration, design alternatives, approval, and Architecture Decision Records.
2. `planning-change-sets` writes concise plans for a different executor model.
3. `test-driving-changes` preserves red-green-refactor with risk-scaled validation.
4. `executing-plans-foreground` makes the current Pi agent the default implementer.
5. `reviewing-change-sets` selects one review mode per checkpoint and validates reviewer claims.
6. `systematic-debugging` requires evidence, one falsifiable hypothesis at a time, and a root-cause regression test.
7. The extension adds a short workflow policy to the system prompt. It does not inject skill bodies or register another skill directory.

Implementation uses the foreground by default. Subagents remain appropriate for bounded read-only exploration, independent review, adversarial review, and explicitly isolated mechanical batches.

## Design interaction

Pi Flow separates approach selection from incremental design approval. When meaningful alternatives exist, the agent presents A/B/C choices with trade-offs and a recommendation. When only one approach is viable, the agent states why and continues without presenting choices.

After the user selects an approach, the agent presents one named design section per turn and asks the user to Accept, Change, or Discuss it. The agent does not advance to the next section until the user resolves the current one. The agent revises unresolved sections before continuing and requests final approval for the integrated design.

Spikes and truly trivial one-section changes may skip this interaction when it would add no decision value. When the user approves the full design at once, asks to batch remaining sections, or explicitly authorizes autonomous or away-from-keyboard execution, the agent stops pausing at intermediate section gates, summarizes the accepted decisions, and proceeds.

## Loop integrity

Never let implementation drift silently from an approved plan. A committed plan changes in the same commit as the implementation departure. A session-local plan records the departure in `progress.md` and `decisions.md`. Design conflicts return to the user.

A systemic root cause that requires architecture, product behavior, or public contract changes returns to `designing-changes`. A reversible mitigation may remain active while that design is considered.

When receiving review feedback, Pi Flow treats each finding as a testable claim. It checks the cited evidence and records Accept, Reject, or needs evidence before implementation.

## Review policy

While Pi Flow is active, `reviewing-change-sets` is the review orchestrator. It is the source of truth for review modes and risk triggers. Do not invoke another review-orchestration skill at the same checkpoint. External skills such as `two-pass-review` are explicit-only and map onto these modes.

Four modes select one review shape per checkpoint:

- `single`: one independent semantic reviewer, for a normal checkpoint or final review.
- `layered`: one semantic and one mechanical reviewer, for mixed or generated changes, or after a prior review missed a mechanical defect class.
- `dual`: two semantic reviewers from different model families, for authentication, permissions, migration, concurrency, billing, public contracts, data-loss risk, or an explicit adversarial request.
- `stacked`: two semantic reviewers from different model families plus one mechanical reviewer.

`stacked` is never selected automatically. High risk selects `dual`, not `stacked`; the third mechanical seat is added only when the user explicitly requests all three seats and accepts the cost. Accepted findings are fixed in the foreground. Re-review follows the `reviewing-change-sets` policy, which is the source of truth for risk triggers.

### Model selection and review scope

Pi Flow does not hardcode review models or constrain selection to two providers. The orchestrator inspects the live model catalog exposed by `subagent_start` in the active Pi session, selects freely across all enabled providers (requiring distinct model families for `dual` and `stacked`), passes exact `provider/model` identifiers, and records each seat's actual model, effort, and role for pull request `AI review` receipts.

Checkpoints run a pre-review diff-size, simplicity, and documentation check before dispatching reviewers. Reviews target coherent milestones rather than per-function micro-diffs, report blocking, high, and medium defects with observable cost, and drop style nits unless requested.

### Independent oracle

More review seats did not stop a repeated escaped defect when every seat inherited the prior reviewer verdict and an implementation-derived heuristic, or when every seat checked only a flawed controller-written summary. Independence is defined by the review oracle, the contract, not by the model family alone. Each semantic reviewer receives the raw user requirements or approved Architecture Decision Record alongside the behavior contract, raw evidence, and paths, and is not primed with the previous verdict or told the current detector is correct. For parsers, rewriters, validators, and other heuristic transforms, the reviewer derives an attack matrix from the contract before judging the implementation. High-risk semantic behavior with no approved contract returns to `designing-changes` before review.

### Repeated-defect stop rule

If two accepted post-fix findings share one semantic seam, the loop stops. Freeze production edits, stop the patch and re-review loop, return to `designing-changes`, write the source-to-output invariant, enumerate the relevant dimensions and pairwise compositions, and approve the contract before another implementation attempt. A third reviewer is not the default response.

### Mechanical review of quantified claims

Mechanical review treats a changed comment or document as testable. A quantified claim using words such as exactly, every, any, only, always, or never requires evidence and a comparison against the implementation. This catches a comment that claims a heuristic detects all unsafe cases.

## Workflow evaluations

Workflow behavior is tested through explicit, multi-turn Pi RPC evaluations. Candidate processes load only Pi Flow and have no tools, context files, or saved sessions. Fresh judge processes grade transcripts as untrusted data. Deterministic assertions and the semantic judge must both pass.

Live evaluations require explicit candidate and judge models. They remain separate from fast, model-free package checks and write uncommitted evidence under `.pi/work/evals/`. Pi Flow does not run model evaluations automatically in Continuous Integration.

## Plan contract

Plans define coherent testable slices. Each slice states its outcome, files and symbols, behavior, test-first contract, dependencies, verification, and review gate. Plans do not prescribe 2–5 minute actions or repeat complete implementation code unless an exact interface is itself the decision.

## Context durability

Active work tracks live session steps in `task_stack` when available, and snapshots durable `implementation-plan.md`, `progress.md`, and `decisions.md` under `.pi/work/<branch>/` at checkpoints or before compaction using full overwrites instead of fragile partial edits. Subagent prompts use artifact paths rather than session history. Controllers use completion notifications and final summaries, never repeated metadata inspection as a waiting mechanism.

The extension skips injecting the orchestrator policy into isolated `pi-sub` child processes (`PI_SUB_AGENT_ID` or `PI_SUB_DEPTH > 0`) so child subagents execute their assigned tasks directly without loading orchestrator skills or spawning nested agents. Root sessions load each matching skill once per context window and reload only after compaction or a phase change.

## Consequences

Pi Flow does not automatically disable Superpowers. Installation instructions must tell users to disable the Superpowers Pi extension and conflicting orchestration skills. Claude Code can continue to use Superpowers unchanged.
